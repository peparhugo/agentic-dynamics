## Problem

L23 (`control_room_apply_skills`) was promoted as `1b1697e1d` on 2026-09-22. Its register row says that the resting screen was restructured and that the adversarial caveats remain: attention/order/age are derived in the browser and the required state screens are only partially rendered. The L23 run clone and `notes/adversarial_review.md` are not reachable from this checkout, so the register row is the candidate record used here. The incumbent render report is evidence of the old candidate-bound room, not proof that the L33 repair is complete.

The repair must preserve the room's truth rule. `apps/control_room/services/operations.py` is the read-model boundary over the one control packet. It owns selection and delivery of recorded state, not causation: it may project packet fields and name a missing or unreadable source, but it must not infer that an agent caused an outcome. Every value must therefore have one of these outcomes:

- recorded: the owning service measured or received the value;
- unbound: the service could not associate the requested value with a record;
- unavailable: the backing store or read model could not be read;
- unknown: the source did not emit the value.

The UI may format those values, but it must not replace them with a browser-clock age, a guessed lifecycle, a first-match attention row, a fabricated zero, or a generic empty table. The acceptance command is the required render profile with candidate identity and real captures: `python scripts/verify_control_room_rendering.py --profile acceptance --candidate <sha>`. The gate's five classes are necessary but not sufficient for this gap unless the fixture and browser probes also assert the server-owned detail and state-screen values below.

### State screens

The accepted state-screen design at `docs/research/control_room_state_screens.md:16-61` defines six operator situations without inventing new lifecycle states. The current room does not render them exhaustively:

- **Running:** raw active rows exist, but there is no server-owned live marker, heartbeat age, or run-level timing in the roster. Owner: operations read model, with heartbeat observation from the control packet. Fixture/gate currently: active rows and scrolling only. Capture: operations roster, but no proof of a live marker.
- **Blocked:** `awaiting_approval` enters attention, but the decision target, authority, eligibility, gate, candidate, and allowed `safe_actions` are not rendered together. Owner: operations read model plus packet actions. Fixture/gate currently: approval attention row only. Capture: attention table, incomplete.
- **Stalled:** an unhealthy-worker count is shown, but no run heartbeat age, affected phase, explicit stall marker, or `{cancel, interrupt}` action set is shown. Owner: operations read model; the supervisor remains observe-only. Fixture/gate currently: one stale worker only. Capture: none.
- **Failed:** failed runs are folded into attention and are not a distinct roster/state screen with terminal reason and evidence. Owner: operations read model and run evidence. Fixture/gate currently: no failed-run seed. Capture: none.
- **Escalated:** attempt escalation fields may exist in the drawer record, but no row or attempt-boundary state screen shows `escalation_from`, `escalation_to`, and reason. Owner: run detail/evidence service. Fixture/gate currently: no escalation fixture. Capture: none.
- **Done:** promotable rows do not distinguish `merged`, `projecting`, and `published`, and no settled receipt/projection state is shown in the roster. Owner: operations read model plus projection watermarks and run evidence. Fixture/gate currently: `promotable` seed only. Capture: operations capture, incomplete.

## Gaps

1. **The server does not yet own the full resting-screen projection.** Add an explicit operations read-model block for deterministic attention order, per-run age/observation metadata, state-screen classification, worker detail, failed-run detail, and safe-action bindings. These must be derived from the packet, control records, and injected observation time. Do not move decision causation into the room.
2. **The current API shape causes client defaults.** `app.js:3154-3180` defaults missing phase halves to zero and renders several unserved facets as generic `unknown`; that is honest for a missing source but it also hides which fields the service already owns. The plan must either bind those fields from the operations payload or name them as unavailable with a source/reason label.
3. **Age/order/attention are still browser decisions.** `app.js:3139-3143,3293-3298,3358-3377` chooses the first attention entry, concatenates rosters, ranks rows, and uses client time through `formatAge()`. The service should emit the ordered rows and a named age observation; the client should render, not decide.
4. **The lifecycle vocabulary is incomplete.** `board-fleet.js:45-53` does not map the control database's operator-relevant states. The repair must preserve raw state and add a named presentation mapping rather than mapping `promotable` to `done` or `awaiting_approval` to `failed`.
5. **The fixture is rich in drawer values but thin in operational states.** Extend `boards_endpoints.json` with safe actions, failed/stalled/escalated/done state seeds, duplicate attention entries, missing/unknown fields, worker identity/reason, and an injected observation time. Keep `run_seed` expansion deterministic and ensure every attention row references a rendered run.
6. **The current acceptance gate proves the old slice, not the L33 caveats.** The required profile runs navigation, loading, degraded, scrolling, and keyboard (`verify_control_room_rendering.py:1844-1855,3844-3868`). It does not assert server-owned order, age, safe actions, worker detail, the six state screens, drawer ledger visibility, hidden log provenance, or a dedicated capture for unknown/error states.
7. **Capture evidence is incomplete.** The current `gate_report.md` records 23 candidate-bound captures for the incumbent profile, but several important values have no dedicated capture. A passing new gate must enumerate the state cases, verify every screenshot exists and is non-empty, bind the candidate SHA, and name omitted coverage honestly.
8. **The L23 candidate artifact is unavailable here.** No run clone or L23 adversarial review could be found under `/repo` or `/tmp`; the L23 register row and current source tree are the provenance boundary. This is a research limitation, not permission to infer findings that are not recorded.
