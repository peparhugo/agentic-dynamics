The Cache-Write Story: Not What It Seems

Why Claude caches context

Claude's prompt caching is designed to reduce latency in multi-turn conversations. Without it, each turn would re-process the full context from scratch — potentially costing more in both time and dollars. Cache writes are the mechanism that makes multi-turn agentic work possible. They are not "waste" — they are infrastructure.

The real question

The question isn't "does Claude waste money on caching?" It's: does Claude's caching implementation result in higher per-session costs than DeepSeek's context management, for equivalent useful work? Our preliminary data suggests yes — but we haven't controlled for model tier, task type, or session count. And Claude's baseline success rate was higher, suggesting cache may be buying better performance on clean tasks at the cost of higher per-session pricing.

Major Gap We have not measured whether Claude's cache writes correlate with improved correctness. The hypothesis that "cache is overhead" is untested — it could be that cache buys correctness at a premium price, which would be a legitimate engineering trade-off, not a flaw.

Known Limitations

Honest accounting of what this preliminary data cannot support.

Critical — No Statistics All operator×strength cells are n=1. No means, standard deviations, or confidence intervals reported. All percentages are point estimates from single observations. Multi-repetition support exists in the experiment runner but has not been executed due to time constraints.
Critical — Correctness is Heuristic "Successful build" uses output_tokens > 500 and keyword detection — not verified test pass/fail. We did not execute the generated code and check test results in a controlled pipeline. The opencode parser extracts test output from bash invocations, but this data is not yet systematically validated.
Critical — Single Task Domain All experiments are Python/Flask web applications (URL shortener, task manager, collaboration platform). No TypeScript, Rust, data analysis, system administration, or other domains tested. Perturbation response may be highly domain-specific.
Major — Unvalidated Classification Manifold vs semantic perturbation classification is a hypothesis, not a measurement. We have not performed embedding analysis to verify that "inject_alien_vocab" actually pushes token embeddings off the typical linguistic manifold. The classification is based on design intent, not empirical validation.
Major — Opencode as Intermediary All experiments run through opencode's agent harness, which may handle tool calling, context management, and session state differently per model. Claude's 0-tool-call behavior on perturbed runs could be an artifact of how opencode invokes Claude, not an inherent property of the model. Direct API comparisons would control for this.
Major — Energy Proxy We use token counts as a proxy for energy consumption, following Liu et al. (2026, arXiv:2605.11733) who argue that LLM inference should be treated as energy-to-token production and call for Joules/token reporting. TokenPowerBench (Niu et al., AAAI 2026) provides empirical J/token measurements across hardware configurations, finding a range of ~0.1–2 J/token depending on model size, hardware, and batch size. Our H100-class estimates (0.08–0.47 J/tok) are conservative and fall within this range. However, we do not know the actual hardware used by either provider. Token counts are directly observed; energy estimates are directional, not precise.
Major — Asymmetric Comparison DeepSeek v4 Pro (mid-tier) vs Claude Fable 5 (premium). The RL-vs-imitation research question requires controlling for model capability tier, which this preliminary data does not do. Haiku 4.5 data (10 sessions, 100% success, $0.009/session) suggests the cost gap is primarily a pricing-tier artifact.
Minor: Cache-write impact on correctness is not measured. Claude had higher baseline success (94% vs 89%), suggesting cache may buy performance. The "waste" narrative is unverified. Pricing changes frequently (Sonnet 5 intro pricing expires Aug 2026) and would alter the analysis. Sample size is heavily skewed toward DeepSeek (45 vs 17 vs 10).

Token-to-Energy Proxy: Not Just Tokens

The energy difference is architectural, not linguistic. MoE sparsity and RL-compressed reasoning change the physics.

Architectural Energy Advantage

DeepSeek v4: Mixture of Experts. 671B total parameters, ~37B active per token (5.5% firing). GRPO compresses reasoning chains into latent-space navigation during training — at inference, solutions are found in the residual stream without generating explicit chain-of-thought tokens. Runs on H800 GPUs (lower TDP, export-restricted hardware).

Claude Fable 5: Dense architecture — all parameters fire on every forward pass. Imitation + RLHF training produces explicit chain-of-thought reasoning. Every reasoning step burns the full model. Runs on newer, higher-TDP hardware (H100-class or newer).

We don't estimate a single energy ratio. We compute a bounded range from observables (tokens) and disclosed parameters (architecture, hardware TDP). The true value lies between the lower and upper bound.

GRPO reasoning compression (latent vs explicit CoT), batch size differences, and PUE would push toward the upper end but are not included — making this a conservative upper bound.

Research Backing

Liu et al. (2026, arXiv:2605.11733) call for LLM inference to be evaluated as energy-to-token production — reporting Joules/token, active binding constraint, and PUE-adjusted delivered power. Their framework directly supports measuring the architectural energy gap we describe.

TokenPowerBench (Niu et al., AAAI 2026) provides empirical J/token measurements showing that model architecture (MoE vs dense), parameter count, and hardware TDP are first-order determinants of inference energy — not just token count. MoE models consistently show 5–20× lower J/token than comparably-sized dense models.

Zhu & Zhu (2026, arXiv:2603.28949) frame AI scaling as a thermodynamic problem: the ultimate bottleneck is Earth's finite heat capacity, not capital or data. Their analysis shows that inference efficiency differences between architectures compound at deployment scale to megawatt-level thermal discharge differentials.

Open Question We cannot measure Joules/token without provider hardware data. But the architectural gap (MoE sparsity, RL-compressed reasoning, hardware TDP differences) means the energy ratio is bounded by parameter activation counts × tokens × hardware efficiency — a 25–200× range, not a 1.3× token-count ratio. Future work: run TokenPowerBench-style measurements against both provider APIs to calibrate the J/token conversion.

What Holds Up Under Scrutiny

Dashboard-verified pricing gap

DeepSeek processed 337M tokens for $7.38 ($0.022/Mtok). Claude Fable 5 costs $10–50/Mtok. The 455–2,273x per-token pricing differential is directly observed from provider dashboards and does not depend on any experiment methodology.

Perturbation response asymmetry (directional)

Claude Fable 5 showed a 34pp drop in code production under perturbation (94% → 60%) while DeepSeek showed no drop (89% → 92%). The n is too small for statistical confidence, but the direction is consistent across both task types tested, and the 0-tool-call pattern (2/5 perturbed Claude runs) is a qualitative difference worth investigating.

Instrument methodology is sound

The experiment pipeline — calibrated perturbation operators, isolated git worktrees per session, opencode agentic execution, cumulative cost accounting from the session database — is well-designed and reproducible. The infrastructure is correct. What's missing is execution (repetitions, multi-tier, multi-domain) and verification (actual test results, not heuristics).

Experiment Design: Multifactorial Compounding

Each session is a game-theoretic round. Perturbation is an intervention. Phase ordering reveals attractor basin depth.

Why One-Shot Experiments Are Insufficient

A single build→test session measures first-order effects: does the model produce correct code under perturbation? But real engineering isn't one-shot. It's understand → build → refactor → extend → maintain. Errors in Phase 2 compound through Phase 4. The model's policy determines whether errors attenuate (conservative, re-derive constraints) or amplify (exploratory, follow novel paths that diverge).

From game theory: each phase is a round of a repeated game. The model's policy is a strategy. Perturbation is an opponent's move. We measure whether the strategy converges to the correct Nash equilibrium (correct solution) or diverges into compounding error. DeepSeek's RL policy was trained on outcome rewards — it converges toward correct solutions even when perturbed. Claude's imitation policy was trained on coherence rewards — it converges toward coherent explanations, not necessarily correct code.
