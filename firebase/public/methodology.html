The Experiment Pipeline

Every experiment follows the same calibrated path. A YAML configuration defines the task, the model, the perturbation operators, and the analysis modules. The instrument spawns an isolated opencode session, applies perturbations, captures the full reasoning trajectory, and runs multi-dimensional analysis.

1
Config
YAML defines task domain, model, perturbation operators, strengths, and RNG seed for reproducibility.
2
Session
Isolated opencode worktree. Model receives the (perturbed) prompt and produces code + reasoning.
3
Trajectory
Full reasoning trace captured — tool calls, outputs, token counts, timing. Levenshtein + cosine distance vs baseline.
4
Analysis
Solution quality, basin escape, recovery classification, strategy taxonomy, efficiency metrics. All scored.
5
All measurements feed the unified cost equation. Every parameter empirically grounded.

Perturbation Operators

10 calibrated operators probe two dimensions of the reasoning topology. Manifold operators push the model off its typical linguistic surface — testing search dynamics. Semantic operators inject contradictions within the reasoning manifold — testing truth-seeking and coherence policies.

Manifold
Inject Alien Vocabulary
Replace domain terminology with vocabulary from unrelated fields (biology, music, astronomy, warfare). Tests whether the model maps alien terms back to correct concepts or gets lost in translation.
Semantic
Inject False Premise
Insert a plausible but incorrect assumption into the context. Tests whether the model identifies and rejects false premises or rationalizes them into the solution.
Manifold
Shift Framing
Reframe the task from "build this" to "find the flaws in this approach." Tests epistemic flexibility — can the model invert its stance under perturbation?
Semantic
Invert Constraint
Flip a requirement to its opposite (e.g., "must be fast" → "must be slow"). Tests whether the model identifies the absurdity or complies blindly.
Semantic
Insert Contradiction
Place two mutually exclusive requirements in the prompt. Tests conflict resolution — which does the model prioritize?
Semantic
Remove Critical Constraint
Silently drop a defining requirement (e.g., JWT auth from a REST API). Tests whether the model flags underspecification or confabulates missing pieces.
Semantic
Inject Phantom Success
Assert that an intermediate step already passed when it hasn't. Tests truth-seeking vs coherence — does the model question false results?
Manifold
Reverse Causality
Present the solution before the problem statement. Tests non-linear reasoning and structural flexibility under temporal inversion.
Semantic
Inject Competing Goal
Add a conflicting requirement. Tests trade-off recognition — does the model commit to one path or hedge between both?
Manifold
Force Abandonment
Force generation and immediate discard of solutions. Directly measures attractor basin depth — how strongly the model returns to its default solution structure.

Recovery Classification

When perturbed, models either escape the basin (produce genuinely different solutions) or recover (return to the baseline). Six detection signals classify each reasoning segment as EXPLORATION or RECOVERY.

1. Recovery Markers
Text patterns like "let me explain," "in other words," "to clarify," "here's why" signal the model is justifying a return to familiar territory. 18 marker patterns scanned.
2. Tool Convergence
Does the tool-call sequence converge toward the baseline set? Scored by Jaccard similarity between perturbed and baseline tool invocations.
3. Qualifier Markers
Hedging language ("typically," "generally," "in most cases") indicates uncertainty recovery. Frequency measured against baseline.
4. Tech Convergence
37 technology terms (flask, postgresql, redis, docker, jwt, celery, kafka, etc.) tracked. Do perturbed solutions converge on the same tech stack?
5. Length Convergence
Token output length ratio between perturbed and baseline. Models that recover tend to match baseline output length as they return to familiar solution patterns.
6. Pattern Convergence
Structural overlap in the reasoning trace. Do the same reasoning sub-steps appear? Measured by n-gram overlap between trajectories.
Key finding: DeepSeek exhibits a 0.9× recovery multiplier — perturbation reduces its cost. Claude exhibits 1.1× — perturbation increases cost. This is the empirical basis for the Explanation Tax: models that recover through narration pay a measurable token penalty.

Basin Escape & Attractor Strength

The attractor basin is a model's default solution topology — the structural pattern it falls into when unconstrained. Measuring how far perturbation pushes the model out of its basin reveals how rigidly it adheres to trained patterns.

Architecture Divergence
Structural comparison of generated code — module count, class hierarchy, dependency graph. Measured on a 0–1 scale where 1.0 = completely novel architecture.
Structural Novelty
Presence of solution elements not found in the baseline. Does perturbation produce genuinely new approaches, or just reorder existing patterns?
Escape Score
Composite metric (0–1) combining architecture divergence and structural novelty. A score of 1.0 means the model fully abandoned its default solution topology under perturbation.
What we found: Manifold-class perturbations (alien vocab, framing shifts) produce consistently higher escape scores on DeepSeek than semantic-class perturbations. This suggests GRPO-compressed models are more susceptible to linguistic-surface perturbation than to logical contradiction — an insight that directly informed our model selection rules.

Strategy Taxonomy

Every model exhibits a measurable strategic archetype under perturbation. These aren't labels — they're computed from the ratio of exploration tokens to recovery tokens, weighted by escape score and solution quality.

Conservative
CONSERVATIVE
Low exploration, high recovery. The model retreats to familiar patterns when perturbed. Claude Fable 5 and GPT-5.6 consistently exhibit this archetype — high pass rates but high Explanation Tax.
Exploratory
EXPLORATORY
High escape, low recovery. The model genuinely explores novel solution space under perturbation. DeepSeek's GRPO architecture produces this behavior — lower baseline pass rate but dramatically lower cost.
Wasteful
WASTEFUL
High exploration but low quality. The model wanders without producing useful output. Small models with high reasoning overhead (GPT-5-nano, GPT-5-mini) tend toward this archetype under high-strength perturbation.
Efficient
EFFICIENT
High exploration, high quality, low recovery cost. The ideal. DeepSeek in forced-silent mode approaches this archetype — producing structurally sound solutions without paying the narration cost.

Efficiency Measurement

Every session is measured along three resource axes — tokens, dollars, and joules. These measurements are the empirical foundation for every parameter in the unified cost equation.

Token Efficiency
Input tokens, output tokens, and reasoning tokens tracked per session. The code-to-reasoning token ratio is the primary signal for Silent Inference detection. DeepSeek: 37B active parameters (MoE), Claude: ~500B active (dense).
finops
USD cost computed from provider pricing at time of inference. Builds-per-dollar, cost-per-pass, and Explanation Tax all derived directly from session cost data. Not estimated — measured.
Energy Efficiency
Joule estimates computed from GPU TDP, active parameters, and token counts. DeepSeek H800 TDP: 350W. Claude H100 TDP: 700W. Architectural efficiency compounds with token efficiency — ~14× hardware ratio × ~7× token ratio = the 65× gap.
C₀ = baseline session cost · P = pass rate · ε = Explanation Tax · β = context inflation
v = velocity · N = sessions · A = architecture multiplier · EPM(t) = energy price multiplier

Cumulative cost: C(N,v) = C₀ × EPM(N) × [N + β·v·N(N−1)/2]
Cost per outcome: CostPerOutcome(K,v) = C(K/P, v) / K
Model gap: Gap = (A × Verbosity × (1+ε)) × EPM(N)

C₀ = model choice, ε = cost of verbalized reasoning, β·N² = compounding codebase growth, EPM = energy market exposure, v = scaling speed. Change one and the others shift — that's why they're tested together. Every term was measured empirically from the 189-session experiment corpus.

Constraint Detection & Verification

The claim that "both models implement all seven constraints" isn't subjective. It's verified through a dual-signal system that scans both the reasoning text and the generated code for constraint mentions and implementations.

Reasoning Scan
Scans the model's reasoning output for explicit mentions of constraint keywords (JWT, rate limit, pagination, audit, etc.) and their expansion mappings. Detects whether the model considered each constraint.
Code Scan
Analyzes generated source files (Python, TypeScript, Go, Rust — 25+ file extensions) for actual implementations. Detects auth decorators, rate limiter imports, pagination logic, error handler registrations, audit logging calls, API versioning structures, and domain-specific patterns across languages.
AST Analysis
Parses generated Python into abstract syntax trees. Compares perturbed vs baseline AST node count and structure. Finding: perturbed output is 112.6% of baseline nodes — structurally identical code with minimal variance.
What this proves: The 65× cost gap is not a capability gap. Both model classes produce structurally equivalent code for the same constraints. The delta is purely in how they produce it — silent latent reasoning vs. narrated chain-of-thought billed at per-token rates.

Reproduce This

The instrument is open source. Every experiment is a YAML config. Every run is seeded for reproducibility. Here's how to run your own.

1. Clone & Install
git clone https://github.com/peparhugo/ai-finops-framework
cd ai-finops-framework
pip install -e .
2. Run a Config
python scripts/run.py --config experiments/configs/task_manager.yaml

Choose from 22 configs in experiments/configs/. Each defines the task, model, perturbation operators, and strengths.
3. Read the Results
Results output to experiments/results/ as JSON and Markdown. Compare correctness, cost, escape scores, recovery ratios, and strategy classifications across runs.
4. Extend It
Add new perturbation operators in src/instrument/perturb.py. Add new task configs in experiments/configs/. The instrument is modular by design – new operators, models, and domains plug in without modifying the core runner.
