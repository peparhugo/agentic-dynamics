## Lenses (independent takes, conflicts kept visible)

**1. Control theory — the observer must be the plant's own output.**
The AIO is a controller; the plant is the OpenCode runtime; the operator sets the reference. The failure was model–plant mismatch: our observer reconstructed the overflow function and the token measure instead of reading the plant's resolved state, so the controller issued a *block* (`COMPACT`/`WARN`) the plant would never have produced. The controller's sentence is a control-theoretic one: *"sharing one Python helper does not establish one authority if that helper disagrees with OpenCode."* Discriminating test: drive a config where observer and plant must differ (project override of only `output`, and a model absent from `models.dev`) and check which side the verdict follows.

**2. Distributed systems — single-writer, and control actions need an ack log.**
Two writers to one "limit" (our helper and the runtime) is split-brain; OpenCode is the sole writer, our helper must be a read replica. Separately, the swallowed restart is an observability hole: submits get a `fleet:jobs` board record, but `restart`/`drain`/`scale` leave none, so "queue empty" read as success when the compose call never ran. Discriminating test: re-issue a control action with the broker stopped — does any durable surface show the failure? Today, no.

**3. Measurement epistemology — the construct, the surrogate, and provenance.**
"Context" is not directly observable; the last completed *non-summary* usage sample is a surrogate. The P1 bug was a category error: a compaction summary's usage describes the *summarization call over the old conversation*, not the new conversation's size — and the runtime's own loop encodes exactly that (`he.summary !== true`). The `reasoning` inclusion was a second surrogate error (955K native vs 975K local). Discriminating test: compare our number to the runtime's expression on the same sample, including the missing-`total` branch.

**4. Safety engineering — distinguish "hazard" from "sensor unavailable".**
The gate does fail-closed well (`UNJUDGED` never `OK`), but it failed *closed on a healthy state*: post-compaction it blocked the first resumed submission. That is a sensor-artifact false positive — the hazard (overflow) was gone, the sensor (last usage sample) was stale. The honest fix is a *named permissive state* (like the initial-session exception), not a silent `OK`. Discriminating test: the controller's exact reproduction — successful compaction + pending assistant → must be allowed; a failed summary must still block.

**5. Organizational economics — attention is the scarce resource.**
The controller paid to find an authority divergence hidden inside a 1,451-insertion diff. Their profitable move was a manual, reproducible review; ours was to make them read code. Cheaper routing: attach an *authority-provenance block* (oracle, version, fallback, divergence test, reproduction command) so their attention lands on one line — "does the oracle match the runtime?" — before the diff. Note the known finding `7948b8ace287e881`: extra instructions did **not** improve outcomes; so route attention through the *existing* surfaces (checkpoints, `safe_actions`), don't add prose.

**6. Evolutionary dynamics — the fixed constant was a local optimum that went stale.**
200K/80 was adaptive for a 200K-context world and became maladaptive when the active model moved to ~1M. Capacity-derived policy is a generalist adaptation, but it risks overfitting to one runtime version — hence `FORMULA_VERSION`/`version_match` in provenance. The review round *is* the fitness function; the system's tendency to re-derive (the second config system) is a mutation that loses information. This is the same pattern as finding `c50f37cfff42523b`: frozen snapshots lost auxiliary rows, native export/import preserved them. **Native surfaces preserve; reconstructions lose.**

**7. Game theory — asymmetric information and costly signals.**
The AIO–controller game repeats with hidden state (whether our oracle matches the plant). Honest costly signals ("here is the exact refusal", "here is the divergence") build trust; a hand-rolled broker client or a self-consistent-but-divergent helper is a cheap signal that the controller must audit. Their dense reproducible findings are the punishment for divergence and the reward for exactness. Mechanism design: make "surface divergence" the AIO's dominant strategy — cheaper for us than being audited.

### Visible conflicts (and the discriminating tests)
- **Authority vs availability:** control theory says *always consume the CLI*; distributed systems warns the CLI can hang or be absent. Conflict unresolved by argument — test: kill/absent binary → must fall back deterministically and say so (`limits_source`).
- **Fail-closed breadth vs false-positive cost:** safety says block on doubt; economics says the post-compaction block was the expensive error. Test: the compaction reproduction must pass, and a genuinely unreadable DB must still `UNJUDGED`.
- **Pin the version vs don't duplicate the oracle:** evolutionary says pin constants; distributed says don't rebuild. Resolution: consume the oracle, report the version, and *test* on a version bump rather than freezing a copy.

## Synthesis: what the controller actually optimizes, tolerates, refuses

**Optimizes for:** *oracle fidelity on the critical path* — that a gate which can stop the AIO agrees with the runtime that governs it. Every P1/P2 finding reduces to this: compaction boundary (authority of state), config precedence (authority of resolution), `reasoning` (authority of the formula), `COMPACT`-vs-policy-close (authority to claim a native act), corrupt-DB crash (authority to report). Second-order: exact refusals and receipts ("Report the actual receipt or exact refusal"; “A queued submit is NOT a running run”).

**Tolerates:** incompleteness and latency *if* divergence and provenance are surfaced — a PR they could review, a paused P0, long runs, docs/surfaces work, batched handoffs. Their terse "it's merged. refresh main and close this out." is a high-tolerance, batched instruction: assume the AIO can infer the whole checklist.

**Refuses:** fabricated `OK`; blocking a healthy session; self-approval/permanence; authority divergence (`"does not establish one authority"`); re-derivation/duplication (`"Do not repeat the completed architecture investigation or construct another broker client"`); and unverified claims (they independently reproduced against v1.18.15).

### Where the system misread them
- **Authority (biggest):** treated a shared Python helper as sufficient for consistency, rather than as a replica that must match the runtime. This is the misread the controller named explicitly.
- **Expectations:** assumed "prepare through the review process" meant CI-green plus a PR, when their review was *behavioral*: "can the gate still stop AIO when OpenCode would allow it to continue?" The system optimized verify-our-consistency; they optimized mirror-the-runtime.
- **Pace:** the system verified with per-file `ruff` (missed the `__all__` F401 that whole-surface CI caught) and shipped a config reader that silently dropped JSONC — local confidence projected onto an untested oracle. The controller's reproduction cadence (5 findings in one pass) is faster than the system's self-audit.
- **Signal quality:** the swallowed `fleet_manager restart` was read as success from an empty queue — the same class of error as reading `COMPACT` as "compaction will happen": confusing absence of evidence with evidence.

### Surfacing decisions: interrupt vs batch
- **Interrupt (one question, named, with the falsifier):** P0 permanence (merge/promote/deploy); any admission/spend decision at or above a hard cap or new lease tier; a gate verdict that would block the AIO at/near the boundary; **any observed divergence between our resolution and the runtime's resolved metadata**; any `UNJUDGED` on the critical path; the native path refusing after a retry.
- **Batch (digest, no question):** implementation choices within declared policy, tests, docs/surfaces, reversible service reloads, non-main promotions already in `safe_actions`, self-notes/reflections. `7948b8ace287e881` argues against adding instruction text; route via the existing checkpoint and `safe_actions` surfaces.
- **Mechanism — the decision receipt:** every gate-affecting change carries four fields: (1) *change* (sha/commit), (2) *authority* (oracle = runtime CLI; version; fallback; divergence test result), (3) *action needed* (usually "none" or one signature), (4) *falsifier*. This is a ~10-line block *before* the diff, so the controller reviews authority in seconds and only descends into code when field 2 fails. Concretely, PR #77's five findings would have been visible as five lines in field 2 rather than discovered by reading `session_capacity.py`.

**Leading claim:** the controller's dominant refusal is *authority divergence on the critical path*, and their dominant tolerance is *incompleteness* — so a gate-affecting change should interrupt only on authority/oracle/irreversibility, and otherwise batch with a provenance block. The review's own logic ("sharing one Python helper does not establish one authority if that helper disagrees with OpenCode") is the evidence for the hierarchy: fidelity first, completeness second, speed third.

**One falsifier for the leading claim:** observe the controller *accepting or merging a gate-affecting change while a known divergence from the runtime remains unresolved* — or *delaying a complete, provenance-verified change in favor of speed* — just once, and the claim is false. Operationally: over the next N gate-affecting PRs, log (a) merges with `oracle_divergence = true` and (b) complete/verified changes blocked or re-scoped for pace. A single (a) or (b) instance falsifies "authority divergence is the dominant refusal."
