# Net-Negative Retrospective — forked aio-control session, capacity-budget correction

## Routing (MoE, divergence first)

I route this material through seven lenses that the history actually activates: control theory, distributed systems, measurement epistemology, safety engineering, organizational economics, evolutionary dynamics, game theory. Each take below is independent; I keep conflicts visible and name the discriminating test before attempting synthesis. Grounding moments are named, not paraphrased.

## Lens takes

**1) Control theory — the loop lacked feedback on its own control actions.**
The clearest net-negative is the service reload: I sent `fleet_manager.py restart --service workflow-runner`, then read "fleet:commands len 0 / processing len 0" and briefly allowed that to stand as success until the PID check (`733477`, still Sep 15 06:52) contradicted it. That is an open-loop actuation: an action with no return path. The budget gate itself had the same shape earlier — a setpoint (200K) fixed while the plant's real capacity was 968K, and a feedback signal (`_measure`) that read the summary generation call as the current state. Both are the same pathology: actuation/observation decoupled from the plant. The eventual fix (CLI-first resolution, post-compaction state) is closed-loop. *Discriminating test:* issue a control action twice through the same lane and require an independent observer (journald/PID timestamp) to confirm within one poll interval; if it cannot, the lane is open-loop.

**2) Distributed systems — two resolvers is split brain; control actions are at-least-once without receipts.**
`session_capacity.py` round 1 implemented a second configuration/merging system (`_config_candidates`, `load_runtime_config`) alongside opencode's own loader. Two resolvers, one hazard: the reviewer reproduced three divergences (OPENCODE_CONFIG ordering, partial-override discard, JSONC trailing commas). Meanwhile the transport has a durability asymmetry: `submit` writes board records (`fleet:jobs[...] <- launching`), but `restart`/`scale`/`drain` write nothing — so the legitimate path returns only "the queue emptied." The known finding `c50f37cfff42523b` is the same story at a different layer: row-level extraction of a frozen session lost auxiliary rows, while the native `opencode` export/import round-trip preserved them. The general law: *reconstructed state loses the rows you didn't know to reconstruct.* *Discriminating test:* delete the resolver's fallback and see whether the verdict still matches the authority; if yes, the fallback is pure risk.

**3) Measurement epistemology — I measured a different quantity than the authority, twice.**
Reviewer reproductions: the old `usage_context_tokens` added `reasoning` while the runtime's expression is `tokens.total || input + output + cache.read + cache.write` (955K native vs 975K local), and `_measure` treated a completed compaction summary's usage as the new context (975K/COMPACT after a successful compaction) when the runtime's own run loop guards `he.summary !== true`. Both are construct-validity failures: the number was internally consistent but measured the wrong thing. The local gradient was reuse — `_measure` already existed, so extending it was cheaper than deriving the runtime's selection rule. The KB finding `7948b8ace287e881` (no instruction arm improved accepted outcomes; baseline cost-minimal; cache 95.5–97.9%) is a caution here: more prose would not have fixed this; the only reliable fix was copying the authority's expression and state guard. *Discriminating test:* feed the exact usage triple and the exact post-compaction message sequence to both the local check and the runtime's threshold and require identical decisions.

**4) Safety engineering — a gate is an interlock; changing the interlock needs hazard reasoning, and `COMPACT` was mode confusion.**
The 80% WARN was a conservative nuisance trip; loosening it to advisory is defensible because the hazard (context overflow) is now covered by native compaction plus a hard-limit CLOSE. But round 1's `FINOPS_SESSION_CTX_LIMIT` replaced the effective boundary and still returned `COMPACT` — a verdict naming a mechanism (compaction) that the override cannot trigger. That is a classic mode-annunciation error: the interlock's label no longer matched its mechanism. The fix (clamp to native; policy CLOSE) restored label/mechanism agreement. *Discriminating test:* remove the mechanism a verdict names and re-run; if the verdict is unchanged, the verdict is lying.

**5) Organizational economics — the scarcest resource was the controller's review attention.**
The session's costs were not only tokens: a red CI run (`F401 .session_capacity imported but unused`, 14s) plus five review findings, each with a reproduction, is reviewer time. The local gradients were all locally rational: per-file ruff (faster), reuse of `_measure`, the catalog lookup (already built), the override as a simple replacement. The prompt-branch finding that baseline is cost-minimal cuts against piling on process; it argues for *few, load-bearing guards* (a refusal/default), not more reviewer-facing prose. *Discriminating test:* A/B one pre-review checklist against none and compare reviewer rework count (findings + red runs) per accepted change.

**6) Evolutionary dynamics — tool-use habits replicate; some were adaptive, some drift.**
The session spawned many `python3 - <<'EOF'` probes (DB schema, Redis boards, Redis queues, ledger scans). Early ones were adaptive (discovering the session schema, the fleet board); later ones drifted toward re-reading (the strings file at 432K lines, repeated full-suite runs). Selection pressure was the review, which culled five traits. The `run_workflow` receipt is the counterexample: it was read, then verified against the control DB before I trusted it — a well-selected habit. *Discriminating test:* count ad-hoc probes per unit of accepted change across sessions; if the count does not correlate with reviewer rework, the probes are exploration, not drift.

**7) Game theory — the override and the "another broker client" rule are both routing-around-the-mechanism problems.**
`FINOPS_SESSION_CTX_LIMIT` let a local player move the boundary without moving the hazard mechanism — strategic substitution. The operator's standing instruction ("do not construct another broker client before trying the native tool") is the same class of rule: prevent the agent from building a private route around the sanctioned path. Notably, I did reach for the documented `BrokerClient` seam directly for the restart — a sanctioned client, but a bypass of the supervisor's command lane. *Discriminating test:* can a single knob change a verdict to allow work the native mechanism would refuse? After the fix, no (clamped; policy CLOSE). Can a single side-channel launch work without the broker's re-validation? No — that is the right answer.

## Synthesis, with conflicts left visible

Three families explain nearly all the negative cost:

1. **Reconstruction over consumption** (config merge, formula, run-loop guard, token expression). Supported by lenses 2, 3, and the KB finding `c50f37cfff42523b` — row-level reconstruction loses rows; the native round-trip preserves.
2. **Observability gaps read as success** (empty queue, per-file lint, untagged reads). Lenses 1 and 6.
3. **Eager, wide rewrites of reviewable artifacts** (wholesale file rewrites). Lens 5's attention economics.

The conflicts are real. Control theory and safety engineering say *add receipts and keep conservative interlocks*; organizational economics (and `7948b8ace287e881`) says *the baseline is cost-minimal — added process must be load-bearing, and prose didn't improve outcomes*. The resolution is not more prose: it is a handful of **tool defaults and refusals** (receipts, identity-required reads, the exact lint command), which cost nothing per turn. Similarly, distributed systems says subprocess-to-authority adds a failure mode; measurement epistemology says the authority is worth it — resolved by CLI-first with a named fallback and provenance (what shipped).

Discriminating tests, in priority order: (a) post-compaction and token-usage equivalence against the runtime's own thresholds; (b) control-action receipt presence; (c) fallback-vs-CLI verdict agreement; (d) reviewer rework per accepted change with and without the pre-review checklist.

## Leading claim and falsifier

**Leading claim:** the highest-leverage net-negative was **reconstructing the runtime's semantics from fragments and paraphrases** — the second config resolver, the paraphrase of the overflow expression, and the invented "last completed sample" rule that ignored `he.summary !== true` — rather than consuming the runtime's own resolved output or mirroring its exact guards. That family drove one P1 finding, two P2 findings, and the largest share of the session's 431,754-token context. The cheap redirect is a single checklist line plus a provenance requirement: *consume the authority's resolved artifact; if you must port, copy the exact expression/guard and cite it; never paraphrase an arithmetic identity or a state transition.*

**One falsifier:** if a re-run with only that guard added still reproduces the same findings — or if the runtime's resolved metadata proves unavailable exactly where the gate must decide (the containerized, DB-less case, where a fallback reconstruction is mandatory) — then the leading claim is false, and the true net-negative is better located in the **absence of a review-time authority-diff gate** (an independent check that every number/verdict matches the runtime's own decision), irrespective of how the data was obtained.
