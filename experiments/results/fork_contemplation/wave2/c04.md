# Entry claim

**Every effectful control act must leave a durable terminal record, and today's submits are the only act that does.**

Stated falsifiably: there exists (at least) one non-submit, effectful control act whose completion is observable *only* by side-effect inspection (PID, journald, container list) and for which no durable, machine-readable record naming the act, its target, its terminal state, and the effect owner's own read-back exists anywhere the next actor can read. I will also sharpen the "only" boundary below, because it is partly false as written and the falseness is load-bearing.

---

# Two lenses, routed before synthesis

**Lens A — Distributed-systems transaction/write-ahead discipline.** An effectful act is a state transition on an *external* plant (Docker, the control db, the KB). Correctness requires three separable objects: an **intent** (claim lane, idempotency key `receipt_id`), an **execution** (the effect owner's call), and a **terminal outcome** written by the party who can observe the plant. The classic failure is exactly what happened: the dispatcher treated "the request left my hands" as terminal, so the outcome had no writer. The lens's invariant: *the terminal record's state field must be a function of the effect owner's evidence, not the dispatcher's return.*

**Lens B — Measurement epistemology / control by authority.** A receipt is a *claim*; the plant's own output is *evidence*. "A queued submit is NOT a running run" is the submit instance of a general rule: every control act's receipt must carry a **read-back of the authority's output** (container instance id + `StartedAt`; run row state; served revision). A restart that returns `returncode=0` with an unchanged instance id is not a completed restart — it is a no-op, and only a read-back can tell.

**Conflict, kept visible.** Lens A wants one atomic writer/store with the terminal state; Lens B says the writer is irrelevant and the store is a red herring — the field is what matters. They *disagree* about whether "who writes it" is load-bearing. Lens A also says the broker (effect owner) should write; Lens B says the broker's *evidence* must be recorded, and if the broker is a stateless request/reply seam with no Redis client, the consumer may write the record **without** weakening the receipt — provided the state field is computed from the broker's fingerprint. I side with B on the mechanism and A on the invariant, and that split drives the migration (no second store; one writer; authority-supplied evidence).

# The acts, their receipts, and the authority read-back

Receipt schema (common), written once per `receipt_id`:

```
schema: control-act-receipt/v1
receipt_id      # = command job_id (minted at enqueue, idempotency key)
action          # submit | restart | scale | drain | cancel | promote | publish
actor, requested_by_session, nonce
target          # service | run_id | spec | release_id
requested_at, started_at, ended_at
state           # accepted | running | completed | failed | refused | no-op | unverified
reason, argv, returncode
evidence        # {before: <fingerprint>, after: <fingerprint>}  ← the authority's output
authority_ref   # pointer to the authority record (run_id/state, approval id, release id)
writer          # component + pid that wrote the terminal state
```

| Act | Receipt fields that matter | Storage | Who writes the terminal state | Verification that the act produced its effect (authority output) | Failure class today |
|---|---|---|---|---|---|
| **submit** | `receipt_id`, `target.spec`, `spec_sha256`, `resume/parent_run_id`, `admission`, `run_id`, `ledger_sha256`, `state` | `fleet:jobs[<job_id>]` (Redis db1) | consumer (`record_job_status`) | control-db `runs` row (`run-<id>`, `state`); run ledger; container process. **The receipt's exit code is a proxy; the run row is the authority.** | "queued ≠ running" — receipt resolves at container exit, not at run-row creation |
| **restart** | `receipt_id`, `target.service`, `evidence.before/after.id+StartedAt`, `returncode`, `state` | **none today** → put in the same `fleet:jobs` hash | consumer, from the broker's fingerprint | `docker-compose -f infrastructure/docker-compose.ladder.yml ps -q <svc>` + `docker inspect -f '{{.Id}} {{.State.StartedAt}}'` before/after; **state=no-op if unchanged** | **swallowed** (claim consumed, released, no record; `_dispatch_command` ignores `outcome["ok"]` for non-submits) |
| **scale** | `receipt_id`, `target.service`, `count`, `evidence.after.count` | `fleet:jobs` | consumer, from fingerprint | `... ps -q <svc> | wc -l` == requested | no record |
| **drain** | `receipt_id`, `target.service`, `evidence.after.count` | `fleet:jobs` | consumer, from fingerprint | `... ps -q <svc> | wc -l` == 0 | no record |
| **cancel** | `receipt_id`, `target.run_id`, `actor`, `state=cancelled`, `authority_ref` | control-db run row (+ decision record) | the control plane (Control Room / `control_run`) | run row `state ∈ {cancelled}`, `ended_at` set; no surviving run container | receipt is the state transition; **actor/reason not on the row** |
| **promote** | approval `{run, gate, candidate, spec, phase}` + signature, `state=promoted`, `authority_ref` | approval artifact in the KB + control-db run state | the control plane **on the operator's signature** | artifact binds the five fields; run row `promoted`; candidate sha matches | durable already (this is where the entry claim's "only" is false) |
| **publish** | approval/release id, signed revision, `state=deployed` | release/approval artifact + served revision | release path on the operator's signature | served revision/hash == the signed artifact | durable already; out of scope for the migration |

**Boundary correction (kept visible, not smoothed):** cancel/promote/publish already leave durable records (run-state transitions, approval artifacts, decision records). The entry claim is therefore precisely true only for the **fleet-compose acts** (submit, restart, scale, drain). The defect is not "non-submits have no records"; it is "the four compose acts have no *uniform, machine-readable, authority-backed* record, and three have none at all." The migration below targets exactly those three.

# Executable artifact (offered as text; not run — analysis only)

A detector that would have caught the swallowed restart, and that generalizes to the compose acts. It reuses `fleet:jobs`, mints a `receipt_id` for control actions, and asserts the receipt's state is a function of the broker's fingerprint. Docstrings and inline comments are the verbose-mode reasoning.

"""Control-act receipts — the swallowed-restart detector (schema control-act-receipt/v1).

Design decisions, stated so they can be argued:
* The terminal state is COMPUTED from the effect owner's read-back fingerprint, never from
  the caller's return. A restart that returns 0 while the container instance id/StartedAt is
  unchanged is `no-op`, not `completed` (Lens B). This is the whole point of the file.
* Storage is the EXISTING `fleet:jobs` Redis hash (db1). No second control store, no new DB,
  no file: a compose act is a sibling of a submit in the same dispatch ledger, distinguished
  by `action`. (Conflict resolved in favour of reuse; see the migration note.)
* The writer is the consumer (the dispatcher), because the broker is a stateless request/
  reply seam with no Redis client. The AUTHORITY field (evidence) is produced by the broker;
  the consumer must not synthesize it. One writer, authority-supplied evidence.
* The receipt is written on EVERY ordinary exit (completed / failed / refused / no-op) and
  released from the claim lane only after the write — otherwise restart self-heals from an
  ambiguous claim with no record, which is the exact class this test guards.
"""
from __future__ import annotations

import json
import pytest

from scripts.fleet import fleet_manager, spawn_wrapper as sw


class _FakeRedis:
    """Minimal hash ops the receipt path uses (matches the real client's shapes)."""

    def __init__(self):
        self.hashes: dict[str, dict[str, str]] = {}

    def hset(self, key, field, value):  # noqa: ANN001 - test double
        self.hashes.setdefault(key, {})[field] = value

    def hget(self, key, field):  # noqa: ANN001
        return self.hashes.get(key, {}).get(field)


def _receipt(client, receipt_id):
    """Read one receipt back — the only read surface the next actor needs."""
    return json.loads(client.hashes["fleet:jobs"][receipt_id])


@pytest.mark.parametrize(
    "action,kwargs,before,after,expected",
    [
        # A real restart: the container identity changes -> completed.

        # THE DETECTOR: compose returns 0 but nothing moved -> no-op, never completed.
        # A claim of success without an authority diff must never be written as success.
        ("restart", {"service": "workflow-runner"},
         {"id": "c1", "started_at": 100}, {"id": "c1", "started_at": 100}, "no-op"),
        # Scale: the read-back count must equal the requested count.
        ("scale", {"service": "workflow-runner", "count": 3},
         {"count": 1}, {"count": 3}, "completed"),
        ("scale", {"service": "workflow-runner", "count": 3},
         {"count": 1}, {"count": 2}, "failed"),
        # Drain: the read-back count must be zero.
        ("drain", {"service": "workflow-runner"}, {"count": 2}, {"count": 0}, "completed"),
        ("drain", {"service": "workflow-runner"}, {"count": 2}, {"count": 1}, "failed"),
    ],
)
def test_compose_act_receipt_state_is_the_authority_diff(
    action, kwargs, before, after, expected, monkeypatch
):
    """A control action writes a durable terminal receipt whose state is the fingerprint diff.

    The broker (effect owner) returns evidence; the consumer computes the state. The test
    injects the broker outcome — the only seam that decides success — so it would fail if the
    consumer ever went back to treating `returncode == 0` (or a print) as terminal.
    """
    client = _FakeRedis()
    receipt_id = f"{action}-test"
    # The broker's typed outcome, exactly the shape run_fleet_command must return: the compose
    # returncode PLUS the before/after fingerprint. `state` here is only the transport state;
    # the RECEIPT state is derived below and must not copy it blindly.
    monkeypatch.setattr(
        sw, "_broker_client",
        lambda: type("B", (), {"fleet_command": lambda self, cmd, dry_run: {
            "state": "OK", "returncode": 0,
            "argv": ["docker-compose", "-f", "ladder.yml", action, kwargs["service"]],
            "evidence": {"before": before, "after": after},
        }})(),
    )
    sw._dispatch_control_with_receipt(client, {"action": action, **kwargs, "receipt_id": receipt_id})

    receipt = _receipt(client, receipt_id)
    # Schema + identity are present regardless of outcome (a failed act still leaves a record).
    assert receipt["schema"] == "control-act-receipt/v1"
    assert receipt["action"] == action and receipt["target"]["service"] == kwargs["service"]
    # THE invariant: the state is the authority diff, not the transport's `OK`.
    assert receipt["state"] == expected, receipt
    # End timestamps exist on every terminal state, including no-op/failed.
    assert receipt["ended_at"] >= receipt["started_at"]

# Smallest migration that closes the swallowed-restart class without a second control store

1. **Mint a `receipt_id` for every control action** at enqueue in `fleet_manager.py::{resize,drain,restart}` (identical to the submit path's `job_id`); carry `actor`/`requested_by_session`. No new key.
2. **Broker returns evidence, not just an exit code** (`launch_broker.py::run_fleet_command` + `_service_fingerprint`). This is the one genuinely new code path, and it is small because the broker already has the compose argv.
3. **Consumer always writes a terminal receipt** to the existing `fleet:jobs` hash (`spawn_wrapper.py::_dispatch_command`), computing `state` from (2); failures go to the existing `fleet_jobs` DLQ via `dlq.record_dead`. One writer; authority-supplied evidence.
4. **Read it back where the actor already looks**: extend `fleet_manager status` to include non-submit receipts, and have `fleet_manager restart` print/exit on the receipt's state so "restart succeeded" is never inferred from the LPUSH return.
5. **Add the detector test** above and wire it into the existing `test_spawn_wrapper.py`/`test_launch_broker.py` families; no schema daemon, no new store, no second board.

The migration's total surface is three files plus one test. The `fleet:commands:processing` claim lane already provides the write-ahead intent; the `fleet_jobs` DLQ already provides terminal failure visibility. What is missing is only the *terminal outcome writer and its evidence* — and those are additive.

# One falsifier for the entry claim

Run the proposed detector's read-back against the *pre-fix history* (or re-issue one control action through a deliberately broken broker on a scratch service): if the first swallowed restart is already identifiable from any existing durable surface — the `fleet:commands:processing` lane's ghost record reconciled by `_recover_processing`, the board, journald, or the compose log — then the claim "no durable terminal record" is wrong (the evidence existed and was merely unread), and the correct migration is a **reader/reconciler**, not the writer described here. That is a real possibility precisely because `_recover_processing` already re-queues control actions, which means the system half-believes it can reconstruct them; if it can, my "smallest migration" is larger than necessary.
